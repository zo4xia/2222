## 一、分级标准

| 级别 | 定义 | 治理紧迫度 | 改动范围 |
|---|---|---|---|
| **L1 轻度** | 命名混乱、重复实现、魔法数字、注释残留、过期函数 | 🟢 可延后 | 单文件、单函数 |

### 5.3 六步心法执行细则

#### 步骤 1 · 插旗标记
- 在代码中用 `// @legacy L3-S01` 或 `// @todo-batch-1` 标记待治理点
- 同步更新本表 `状态` 列为 `🔨 治理中`
- 不删除原代码，只加标记

#### 步骤 2 · 最小单元划分
- 每个治理项只解决一个问题
- 禁止「顺手优化」「顺手重构」
- 治理项跨文件时，列出所有受影响文件

#### 步骤 3 · 逐模块提取
- 拆分超限文件时，按职责拆分（UI/业务/数据/工具）
- 公共函数提取到独立模块（如 `server/projectCode.js`、`server/backup.js`）
- 不破坏现有 API 接口

#### 步骤 4 · 改一测一
- 每改完一项，立即跑对应验证：
  - 后端：`npm run check:proxy` + `npm run check:knowledge`
  - 前端：`npm run lint` + 浏览器手测
  - lint 通过 ≠ 验证通过，必须有运行时证据
- 验证失败回滚，不堆积技术债

#### 步骤 5 · 风险可控
- 每批次治理后跑一次全链路冒烟（Step1→handoff→B→Check→TTS→deliverable）
- 不阻断主链路：A/B 主链不重构、不搬动、不替换（用户铁律）
- 改动留 diff 截图到 ENGINEERING_LOG
