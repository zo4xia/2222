### 1.3 架构分析

项目核心架构：
```
Step1Entry.vue (第1步: 识别 + 落画布)
   ↓ POST /api/handoff
DirectFlow.vue (页面切换 + handoff 文件读取)
   ↓ GET /api/handoff

   ↓ openHanddrawPlayer

```

数据传递有 3 个并行通道：
1. **localStorage 通道**（`agent-b-deliverable`）：openHanddrawPlayer 写 → row-player 读 ← **当前断点**
2. **URL query 通道**（`?deliverable=/path/to/rows.json`）：row-player 支持，但 openHanddrawPlayer 不用
3. **文件通道**（`public/deliverable/current.json`）：generateDeliverablePage 写，row-player 通过 URL query 读

## Phase 2：方案探索

### 2.1 针对每个核心痛点的方案对比

#### 痛点 P1+P3：row-player.html 不读 localStorage（演播录制看到旧题）

##### 方案 A：最小手术 - 把备份版的 localStorage 读取逻辑合并回现版 row-player.html

**操作**：从 `row-player.html.bak-20260921-pre-task10` line 1188-1210 抠出 localStorage 读取段，合并到现版 `public/deliverable/row-player.html` 的 `loadFromUrlOrDefault` 函数里。同时把写死的 `<title>` 改成动态（`document.title = DATA.problemText || '板书演播'`）。

**优点**：
- 改动量最小（~20 行代码）
- 保留上传版 v1.1 的所有甲方要求（38px / 平方乔木体 / 1.7 行高 / ±5% 速度）
- 保留上传版的所有内嵌素材、AgentCanvas 控制桥、v1.1 升级
- 数据传递链路立即恢复

**缺点**：
- 上传版和备份版需要手工合并（备份版有 normData/normRow 字段归一逻辑，必须一并合并）
- 合并后需要重新跑一次端到端验证

**评分**：技术可行性 5 / 开发成本 5 / 维护成本 5 / 性能影响 5 / 扩展性 4 / 风险 5 / **可衍生性 4** / **UI/UX 5**

##### 方案 B：URL query 通道取代 localStorage

**操作**：改 `openHanddrawPlayer`，不写 localStorage，改成 `window.open('/deliverable/row-player.html?deliverable=/api/deliverable/current.json', '_blank')`。需要先调 `generateDeliverablePage()` 确保最新数据已写入 `public/deliverable/current.json`。

**优点**：
- row-player.html 不用改（URL query 通道现成支持）
- 数据是文件级持久化，刷新不丢
- 多人协作场景下，URL 可分享

**缺点**：
- 需要"演播录制"前先确保 `current.json` 是最新的（增加一步）
- 文件写入有 IO 延迟，可能 race condition
- 改变了用户预期（"演播录制"按钮原本是即点即开）

**评分**：技术可行性 5 / 开发成本 4 / 维护成本 5 / 性能影响 4 / 扩展性 5 / 风险 4 / **可衍生性 3** / **UI/UX 3**

##### 方案 C：双通道 + 优先级降级

**操作**：row-player.html 改 `loadFromUrlOrDefault` 为三段式：
1. 先读 URL query（`?deliverable=...`）
2. 再读 localStorage（`agent-b-deliverable`）
3. 再读默认 `/api/deliverable/current.json`
4. 最后降级到内嵌 DATA

**优点**：
- 三通道冗余，最稳
- 用户无论是"演播录制"按钮点开、还是分享 URL、还是直接访问，都能看到正确数据
- 可衍生性强（后续加 cookie/indexedDB 通道也容易）

**缺点**：
- 改动量略大（~30 行）
- 需要写好优先级文档，避免后续维护混乱

**评分**：技术可行性 5 / 开发成本 4 / 维护成本 4 / 性能影响 5 / 扩展性 5 / 风险 4 / **可衍生性 5** / **UI/UX 5**

#### 痛点 P5：`__VUE_HMR_RUNTIME__ is not defined`（★ 阻断性 bug，必须最先修）

> **本节为 Task 11 诊断完成后用户实测时发现的阻断 bug，追加为最高优先级改进项（改进 0 紧急修复，优先于改进 1-10）**

##### 真实错误堆栈（用户提供）

```
ReferenceError: __VUE_HMR_RUNTIME__ is not defined
    at /src/components/BoardContentLayer.vue:898:3
    at /@vite/client:531:53
    at Array.map (<anonymous>)
    at HMRClient.notifyListeners (/@vite/client:531:41)
    at handleMessage (/@vite/client:1028:26)
    ...
```

##### 根因分析（铁证，非推测）

**Vite 转译后的 BoardContentLayer.vue 实际内容**（curl `http://localhost:3000/src/components/BoardContentLayer.vue` 实测）：

```js
import { createHotContext as __vite__createHotContext } from "/@vite/client";
import.meta.hot = __vite__createHotContext("/src/components/BoardContentLayer.vue");  // ← Vite 注入 HMR 钩子
import { computed, nextTick, ... } from "https://esm.sh/vue@3.5.39"                  // ← vue 走 esm.sh 生产版
//                                                       ↑ esm.sh 的 vue 是生产版本，不含 __VUE_HMR_RUNTIME__
```

**链路**：
1. Task 1/6 `vite.config.js` 的 `cdnExternalPlugin` 把 `vue` external 到 `https://esm.sh/vue@3.5.39`
2. `@vitejs/plugin-vue` 在 dev 模式为每个 .vue 文件注入 `import.meta.hot = __vite__createHotContext(...)` 用于 HMR
3. 当 .vue 文件代码改动（非注释），Vite 触发 HMR 重建 → 调用 vue 内部的 `__VUE_HMR_RUNTIME__.rerender(component)` 或 `__VUE_HMR_RUNTIME__.reload(component)`
4. 但 esm.sh 的 vue 是**生产版本**，没有导出 `__VUE_HMR_RUNTIME__` 全局变量
5. → `ReferenceError: __VUE_HMR_RUNTIME__ is not defined`

**关键验证**：
- `curl -s "https://esm.sh/vue@3.5.39"` → 返回 `/* esm.sh - vue@3.5.39 */` 代理转发到 `runtime-dom.mjs`，**生产版无 HMR runtime**
- `@vue/runtime-core` 的 dev 版本才导出 `__VUE_HMR_RUNTIME__`，esm.sh 默认拉生产版

##### 方案 A：dev 模式不 external vue，build 模式才 external

**操作**：改 `vite.config.js` 的 `cdnExternalPlugin`，加 dev/build 模式判断：

```js
function cdnExternalPlugin() {
  const isDev = !!process.env.VITE_DEV  // 或用 command 参数
  return {
    name: 'cdn-external-plugin',
    enforce: 'pre',
    resolveId(source, importer) {
      // ... 其他不变
      const cdnUrl = toCdnUrl(source)
      if (!cdnUrl) return null
      // ★ dev 模式 vue 走本地 node_modules（含 HMR runtime）
      if (isDev && source === 'vue') return null  // 不 external，让 vite 用本地 vue
      return { id: cdnUrl, external: true }
    },
  }
}
```

或更简洁：

```js
// 定义 CDN 列表时按模式分
const CDN_EXTERNAL_PKGS = process.env.NODE_ENV === 'production'
  ? ['vue', 'ant-design-vue', '@ant-design/icons-vue', 'katex', 'rough-notation', 'roughjs']
  : ['ant-design-vue', '@ant-design/icons-vue', 'katex', 'rough-notation', 'roughjs']  // dev 不含 vue
```

**优点**：
- dev 模式 vue 走本地 node_modules（含 HMR runtime），HMR 正常工作
- build 模式 vue 仍走 CDN（生产环境无 HMR 需求）
- 改动最小（仅改 cdnExternalPlugin 逻辑）
- `optimizeDeps.exclude` 里也要对应去掉 vue（让 vite 预打包 vue 到 .vite/deps）

**缺点**：
- dev 模式 vue 走本地，首屏加载比纯 CDN 略慢（但只慢一次，预打包后秒开）
- ant-design-vue 仍 external 到 esm.sh（用 `?deps=vue@3.5.39` pin 同一 vue）—— **但这要求 ant-design-vue 也能找到本地 vue 实例**，可能需要 `optimizeDeps.include: ['ant-design-vue']` 或别名

**评分**：技术可行性 5 / 开发成本 5 / 维护成本 5 / 性能影响 4 / 扩展性 4 / 风险 4

##### 方案 B：dev 模式从 vue 的 dev 分支拉 CDN

**操作**：CDN URL 改为 `https://esm.sh/vue@3.5.39?dev` 或 `https://esm.sh/vue@3.5.39/dist/vue.runtime.esm-bundler.js`：

```js
const CDN_URLS = {
  vue: process.env.NODE_ENV === 'production'
    ? `https://esm.sh/vue@${CDN_VERSIONS.vue}`
    : `https://esm.sh/vue@${CDN_VERSIONS.vue}?dev`,  // esm.sh 的 dev 分支含 HMR runtime
  // ...
}
```

**优点**：
- 所有模式都走 CDN（保持 Task 1 设计意图）
- esm.sh 支持 `?dev` 参数拉开发版

**缺点**：
- esm.sh 的 `?dev` 版本可能仍有差异（HMR runtime 导出方式可能不兼容 Vite 注入的 `__VUE_HMR_RUNTIME__` 全局）
- 风险高（esm.sh 内部实现可能变）
- 即使拉 dev 版，`__VUE_HMR_RUNTIME__` 是 Vite/`@vitejs/plugin-vue` 注入的全局变量，需要 vue runtime 把 HMR API 写到 window.__VUE_HMR_RUNTIME__ 上，esm.sh 的 dev 版本未必这么做

**评分**：技术可行性 2 / 开发成本 5 / 维护成本 2 / 性能影响 5 / 扩展性 2 / 风险 1（高风险）

##### 方案 C：dev 模式 vue 走 vite 预打包（不用 CDN），build 模式 vue 走 CDN

**操作**：
1. `cdnExternalPlugin` 的 `resolveId` 在 dev 模式遇到 `vue` 返回 null（不 external，让 vite 用本地 node_modules）
2. `optimizeDeps.exclude` 删掉 `vue`（让 vite 预打包 vue 到 `.vite/deps/vue.js`）
3. `optimizeDeps.include` 加上 `vue`（强制预打包）
4. ant-design-vue 的 `?deps=vue@3.5.39` 仍生效（esm.sh 把 vue 作为 dep 一起拉，但因为是同一版本号，会和本地 vue 实例兼容）

**优点**：
- dev 模式 vue 走 vite 预打包（含完整 HMR runtime + dev tools）
- HMR 完全正常
- 风险最低

**缺点**：
- dev 模式 vue 不走 CDN，违背 Task 1 设计意图（但只影响 dev，不影响 build）
- 首次启动 vite 会重新预打包 vue（冷启动慢 5-10 秒）

**评分**：技术可行性 5 / 开发成本 4 / 维护成本 5 / 性能影响 4 / 扩展性 4 / 风险 5（最低风险）

##### 推荐：方案 C

**理由**：
- 风险最低（方案 B 风险最高，方案 A 改 ant-design-vue 别名有连锁问题）
- dev 性能影响最小（vite 预打包后毫秒级加载）
- build 模式 100% 保留 Task 1 的 CDN 优化
- 用户痛点是"无法继续任何修改"（HMR 坏了），方案 C 直接解决根本问题

#### 痛点 P6：`Failed to resolve module specifier "vue". Relative references must start...`（★ 部署环境阻断 bug）

> **本节为 Task 11 第二轮诊断追加，与 P5 同源但发生在部署环境（tttser.zeabur.app）**

##### 真实错误（用户提供）

```
tttser.zeabur.app/:1 Uncaught TypeError: Failed to resolve module specifier "vue".
Relative references must start with either "/", "./", or "../".
```

##### 根因分析（铁证）

**问题根源**：`vite.config.js` 的 `cdnExternalPlugin` 用 Vite 的 `resolveId` 钩子 + `{ external: true }` 返回 CDN URL，**只在 dev server 模式生效**。

**build 模式配置**（`vite.config.js` line 152-156）：
```js
build: {
  rollupOptions: {
    external: Object.keys(CDN_URLS).concat(['roughjs/bundled/rough.esm.js']),
    // ↑ 这里只把包名标为 external，rollup 不打包它们
    // 但 rollup 不会自动改写 import 为 esm.sh URL！
  },
}
```

**问题**：
1. dev 模式：`cdnExternalPlugin` 的 `resolveId` 把 `import 'vue'` 改写为 `import "https://esm.sh/vue@3.5.39"` ✓
2. build 模式：`rollupOptions.external: ['vue', ...]` 让 rollup **跳过** vue 不打包，但**不改写 import 语句**
3. 构建产物 `dist/assets/main-xxx.js` 里仍是 `import { createApp } from "vue"`（裸 specifier）
4. 浏览器原生 ESM 不支持裸 specifier，报错：`Failed to resolve module specifier "vue". Relative references must start...`

**Zeabur 部署环境**（`tttser.zeabur.app`）跑的就是 build 产物，所以报这个错。

**关键证据**：
- `vercel.json` line 3: `"buildCommand": "npm run build"` + `"outputDirectory": "dist"`
- `package.json` line: `"build": "vite build"` —— 部署时跑 vite build
- 项目本地无 `dist/` 目录（用户从来不本地 build，只在沙箱 dev）
- 但 Zeabur 部署会跑 `npm run build` → 产物含裸 import → 浏览器报错

##### 方案 A：build 模式也用 cdnExternalPlugin 的 URL 改写

**操作**：在 `cdnExternalPlugin` 里加 `renderChunk` / `generateBundle` 钩子，build 模式手动把产物里的 `from "vue"` 改写为 `from "https://esm.sh/vue@3.5.39"`：

```js
function cdnExternalPlugin() {
  return {
    name: 'cdn-external-plugin',
    enforce: 'pre',
    resolveId(source, importer) { /* 不变 */ },
    // ★ build 模式：渲染最终 chunk 时改写 import 语句
    renderChunk(code, chunk) {
      let result = code
      for (const [pkg, url] of Object.entries(CDN_URLS)) {
        // 改写 bare import 为 CDN URL
        const regex = new RegExp(`(from\\s*["'])${pkg}(["'])`, 'g')
        result = result.replace(regex, `$1${url}$2`)
      }
      return result
    },
  }
}
```

**优点**：
- dev + build 双模式都走 CDN
- 不需要 importmap

**缺点**：
- 正则改写 import 有风险（可能误改字符串里的 "vue"）
- 复杂场景（动态 import、字符串拼接 import）可能漏改

**评分**：技术可行性 3 / 开发成本 3 / 维护成本 2 / 性能影响 5 / 风险 2

##### 方案 B：用 Vite 的 importmap + esm.sh importmap（推荐）

**操作**：`vite.config.js` 加 importmap 配置，build 模式在 index.html 注入 importmap：

```js
// vite.config.js
import { injectImportmap } from 'vite-plugin-importmap'  // 或手写

const importmap = {
  imports: {
    vue: 'https://esm.sh/vue@3.5.39',
    'ant-design-vue': 'https://esm.sh/ant-design-vue@4.2.6?deps=vue@3.5.39',
    // ... 其他 CDN_URLS
  }
}

export default defineConfig({
  plugins: [
    // 注入 importmap 到 index.html
    {
      name: 'inject-importmap',
      transformIndexHtml(html) {
        return html.replace(
          '<head>',
          `<head><script type="importmap">${JSON.stringify(importmap)}</script>`
        )
      }
    }
  ]
})
```

**优点**：
- 浏览器原生 importmap 标准，最稳定
- 裸 specifier `import "vue"` 通过 importmap 解析为 CDN URL
- dev + build 双模式一致

**缺点**：
- 需要手写 importmap 或用第三方插件
- importmap 浏览器支持需 Chrome 89+ / Safari 16.4+（基本覆盖）

**评分**：技术可行性 5 / 开发成本 4 / 维护成本 5 / 性能影响 5 / 风险 5

##### 方案 C：build 模式不让 vue external，让 rollup 打包进产物

**操作**：把 `build.rollupOptions.external` 改为**只含 ant-design-vue / katex / rough-notation / roughjs**，不含 vue：

```js
build: {
  rollupOptions: {
    external: [
      'ant-design-vue', '@ant-design/icons-vue',
      'katex', 'rough-notation', 'roughjs', 'roughjs/bundled/rough.esm.js'
    ],  // ★ 不含 vue
  },
}
```

但这样 vue 会被 rollup 打包进 chunk，ant-design-vue 仍 external 但找不到 vue。

**兜底**：build 模式全部不 external，让 rollup 全部打包进产物（产物大但能跑）。

**优点**：
- 改动最小（删一行 external）
- build 产物自包含，部署不需要 importmap

**缺点**：
- 产物体积变大（vue ~80KB + ant-design-vue ~300KB 全打包）
- 违背 Task 1 的 CDN 优化初衷
- build 模式首屏加载变慢

**评分**：技术可行性 5 / 开发成本 5 / 维护成本 4 / 性能影响 2 / 风险 4

##### 推荐：方案 B（importmap）

**理由**：
- 浏览器原生标准，最稳定
- dev + build 双模式一致（Task 1 设计意图保留）
- 不用改正则不用改产物代码
- 和方案 C 的 P5 修复（dev 模式 vue 走 vite 预打包）**正交**，可以同时存在

**重要**：P5 和 P6 是两个独立问题，必须**分别**修复：

##### 改进 0.5（紧急修复 P6，紧随改进 0 之后）：build 模式加 importmap

**操作目标**：`vite.config.js` + `index.html`

**变更描述**：
1. `vite.config.js` 加 importmap 注入插件（手写或用 vite-plugin-importmap）

## 附录 B：Deepthink Protocol 决策记录

### B.1 为什么选方案 C 而不是 A

**场景**：演播录制数据传递，方案 A 最小手术但只走 localStorage，方案 C 三通道降级。

**决策**：
- localStorage 在隐私模式 / 跨域 iframe 时会被禁用
- 文件通道（current.json）可以跨设备分享 URL
- 三通道降级几乎是 0 成本（多 ~20 行代码），但带来极大的健壮性
- 用户的痛点 P1+P3 已经说明"数据没传递"是严重问题，需要彻底解决而不是头痛医头

### B.2 为什么不重构 row-player.html

**场景**：row-player.html 1388 行单文件，内嵌 base64 + CSS + JS，看起来很臃肿。

**决策**：
- 用户明确禁止重构
- row-player.html 是"单文件离线产品"设计哲学（line 8 注释：`模板壳 / 母版：单文件、零依赖、离线双击可开`）
- 拆分会让"双击离线打开"特性失效
- 改动应该是最小手术（合并 localStorage 逻辑 + 去 BOM）

### B.3 为什么先做改进 1 而不是改进 5 清理

**场景**：用户说"清理旧版本残留"，可能期望先清理。

**决策**：
- 改进 5 删 `row-player.html.bak-20260921-pre-task10` 前，必须先把备份的 localStorage 逻辑合并到现版
- 如果先删备份，改进 1 就无法做（需要从备份里抠代码）
- 所以顺序必须是：改进 1 → 改进 5

### B.4 为什么改进 9 是 Node.js 脚本而不是浏览器自动化

**场景**：QA 测试可以跑 Node.js 脚本或 agent-browser。

**决策**：
- agent-browser 每次跑要 ~10 秒，每次改进后跑一次太慢
- Node.js 脚本跑 ~1 秒，可以高频跑
- 浏览器交互测试（如黄金路径）仍需 agent-browser 手工跑（在 Phase 5 验收清单 V1-V10 里）
- Node.js 脚本只做"代码静态检查 + 服务端 API 检查"

### B.5 为什么不修 Next.js 抢端口问题

**场景**：Next.js 反复抢 3000 端口，每次都要 pkill。

**决策**：
- 这是沙箱环境问题，不是项目问题
- 项目代码里改 next dev 端口属于偏离主题
- 放到附录 A.5 作为 v3 升级方向，不在本次改进范围
